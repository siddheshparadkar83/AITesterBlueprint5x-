04 — Test Case Execution

Use this guide to create a defensible execution record for an existing test suite. Record statuses only from actual supplied evidence; never infer or assume a result.

Use when You are running existing test cases against a build and need an evidence-backed execution record.
Skip when Test cases do not exist yet. Use 02-test-case-design-RICEPOT.md.

How to use this guide

  1. Supply the existing test cases, their steps and expected results, the build and environment, and the execution window.
  2. Provide actual observations and evidence for the steps that were run.
  3. Copy the prompt below into your AI tool and fill in the context. Do not ask it to invent test results or defect IDs.
  4. Review step-level and case-level statuses, blockers, failures, evidence references, and the summary arithmetic.

Important: If a step could not be executed, mark the case Blocked. A case cannot be Passed without evidence for every step.

Allowed statuses

Use only these exact status values:

  • Passed — the observed result matches the expected result and evidence is supplied for every step.
  • Failed — the actual observed result does not match the expected result.
  • Blocked — a step could not be executed; state what blocked execution.
  • Not Run — execution was not performed.
  • Skipped — execution was intentionally skipped.

When evidence for a step is missing, record No evidence supplied. Do not assign a defect ID unless one was provided.

Prompt template

Copy this prompt and provide the test cases and execution evidence. Keep the limits in place to ensure results are traceable to what was actually executed.

### C — Context
I am executing the following test cases against a live build.
- Product / module: [PRODUCT, MODULE]
- Build / version: [BUILD ID]
- Environment: [URL, BROWSER + VERSION, OS, DEVICE]
- Execution window: [DATE-TIME START → END]
- Test cases to execute: [PASTE CASE IDs AND STEPS]
- Evidence captured: [SCREENSHOTS, LOGS, HAR, VIDEO — or "None"]

### L — Limits
- Use ONLY the supplied test cases. Do not add, rewrite, or "improve" them.
- Record status only from actual evidence supplied. Never assume a result.
- Allowed statuses, exactly: Passed / Failed / Blocked / Not Run / Skipped.
- If a step could not be executed, the case is Blocked — not Passed.
- If evidence is missing for a step, mark that step "No evidence supplied."
- Do not assign defect IDs you were not given.

### E — Examples
| VWO-LOGIN-TC-001 | Step 1 | Open https://app.vwo.com/ | Login page loaded | Passed | Screenshot 01 |
| VWO-LOGIN-TC-004 | Step 4 | Submit with blank password | Submit blocked with validation | Failed | Screenshot 04 — form submitted |
| VWO-LOGIN-TC-007 | Step 2 | Enter locked-account credentials | Login rejected | Blocked | No locked test account available |

### A — Action
Produce an execution record for every supplied test case: per-step status,
overall case status, observed result, evidence reference, and defect reference
where a case failed.

### R — Review
Before returning, verify:
- No case is Passed without evidence for every step.
- Every Failed case has an observed actual result and a defect reference or an
  explicit "Defect not yet raised."
- Every Blocked case states what blocked it.
- Overall status is consistent with the worst per-step status.

Output contract

The execution record must include all five sections:

SectionRequiredShape
Execution SummaryYesTotal / Passed / Failed / Blocked / Not Run / Skipped + pass rate
Step-Level LogYesTC ID | Step | Action | Expected | Status | Evidence
Case-Level ResultYesTC ID | Overall Status | Observed Result | Defect Ref | Notes
FailuresYes (or “None”)TC ID | Step | Expected | Actual | Suggested Severity
BlockersYes (or “None”)TC ID | What Blocked Execution | Owner To Unblock
  • No case may be Passed without evidence.
  • Do not invent defect IDs.
  • Summary counts must equal the corresponding table rows.

Self-check

Before returning the execution record, verify each item:

  • Every supplied test case appears exactly once in the case-level result.
  • Every Passed case has evidence against each of its steps.
  • Every Failed case has a concrete observed actual result.
  • Every Blocked case names the blocker and the owner who can unblock it.
  • No status outside the five allowed values is used.
  • Summary arithmetic matches the tables.

SKILL.md conversion

To package this execution workflow as a skill, use the following metadata:

---
name: test-case-execution
description: Produce an evidence-backed execution record — per-step log, case-level status, failures, and blockers — using only the supplied test cases and without inventing results. Use when running a test suite against a build.
---

Trigger phrases

“record execution results”, “log test run”, “execution report for this build”, “run these test cases and record status”.

Procedure for the skill body

Load cases → execute/record per step → roll up case status → list failures → list blockers → verify no unearned Passed → self-check.

Alternative: If a failed case needs to become a filed defect, hand the failure row to 03-bug-report-CRISP.md.
