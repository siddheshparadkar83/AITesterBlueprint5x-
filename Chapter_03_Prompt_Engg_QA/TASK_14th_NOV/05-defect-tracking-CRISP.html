05 — Defect Tracking

Use this guide to maintain one consistent row per defect across a test cycle, with clear state, ownership, ageing, and duplicate links.

Use when You are maintaining a defect log and need consistent tracking and summary reporting.

How to use this guide

  1. Collect the defect list, reporting period, release or build, and team roster or owner roles.
  2. Set the ageing SLA in days. If none is provided, the default is 5 days.
  3. Copy the prompt below into your AI tool and supply the source defects without removing their IDs.
  4. Review the normalized register, suspected duplicate links, ageing flags, summaries, and missing-field list.

Important: Do not invent missing dates, owners, or build numbers, and do not close or mark a defect Fixed without supplied evidence.

Tracking rules

  • Preserve supplied defect IDs exactly; never renumber them.
  • Represent each distinct defect in one row. Link probable duplicates instead of deleting them.
  • Use only the allowed states: New, Open, In Progress, Fixed, Retest, Closed, Reopened, Deferred, or Rejected.
  • Compute age in days from the raised date to today; flag defects open beyond the stated SLA.
  • Use the defined severity scale (Critical / High / Medium / Low) and priority scale (P1 / P2 / P3 / P4).
  • Sort the main register by severity, then age descending. Group summary counts by severity and by module.

Prompt template

Copy this prompt and provide the defect log, reporting window, build, and owner information. Keep the fixed columns and allowed states consistent.

### C — Context
I maintain the defect log for [PROJECT / RELEASE]. Defects arrive from several
testers and are tracked in [JIRA / AZURE DEVOPS / SHEET].
- Reporting period: [START DATE → END DATE]
- Release / build under test: [BUILD ID]
- Defects supplied: [PASTE DEFECT LIST OR TABLE]
- Team roster / owners: [NAMES OR ROLES]

### R — Role
Act as the QA lead accountable for defect hygiene: nothing untracked, nothing
duplicated, nothing ageing silently.

### I — Instructions
1. Normalise every defect into one row using the fixed column set below.
2. Preserve any supplied defect IDs exactly. Never renumber them.
3. Detect probable duplicates and link them instead of deleting them.
4. Assign state using only: New / Open / In Progress / Fixed / Retest / Closed / Reopened / Deferred / Rejected.
5. Compute age in days from raised date to today.
6. Flag every defect open beyond [SLA DAYS] as ageing.
7. Group defects by severity and by module for the summary.
8. Identify defects missing a mandatory field and list them separately.

Do NOT:
- Change a supplied severity without stating the change and the reason.
- Close or mark Fixed a defect without supplied evidence.
- Invent missing dates, owners, or build numbers.

### S — Style
Tabular and terse. One row per defect. No narrative inside cells beyond the
summary fields.

### P — Parameters
- One row per defect, no merging of distinct issues.
- Missing values: "Not supplied."
- Ageing threshold: [SLA DAYS, default 5].
- Severity: Critical / High / Medium / Low. Priority: P1 / P2 / P3 / P4.
- Sort the main table by severity, then by age descending.

  • Supplied IDs must remain unchanged.
  • No defect may be marked Closed without evidence.
  • Duplicate links must be bidirectional.

Self-check

Before sharing the tracking report, verify each item:

  • Every supplied defect appears exactly once in the register.
  • All states come from the allowed list.
  • Age is computed, not guessed, from the raised date.
  • Ageing flags use the stated SLA, consistently.
  • Duplicates are linked, not deleted.
  • Severity totals equal register row totals.
